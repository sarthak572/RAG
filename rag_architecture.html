1. Data Ingestion & Indexing Pipeline

Purpose

Transform raw documents into queryable embeddings. This is a critical offline process that happens before any queries.

Key Responsibilities:
  • Extract and normalize data from multiple sources
  • Split documents into optimal chunks
  • Generate embeddings for each chunk
  • Store in vector database with metadata
  • Handle updates and deletions

1.1 Data Source Connectors

What it does: Pulls data from various sources and normalizes it
Sources: ├── Databases (PostgreSQL, MongoDB) ├── File systems (S3, GCS, Azure Blob) ├── APIs (GitHub, Jira, Confluence) ├── Web crawlers ├── Real-time streams (Kafka, Pub/Sub) └── Structured data (CSVs, JSON) Process: 1. Connect & authenticate to source 2. Extract data in batches or streaming 3. Handle incremental updates (CDC - Change Data Capture) 4. Parse different formats 5. Normalize into common schema

1.2 Document Preprocessing

What it does: Cleans and prepares raw documents
Steps: 1. Text extraction (PDFs, images via OCR) 2. Language detection 3. Encoding normalization (UTF-8) 4. HTML/XML parsing and tag removal 5. Removing boilerplate content 6. Deduplication 7. Filtering (remove spam, inappropriate content) 8. Schema validation

1.3 Chunking Strategy

What it does: Splits documents into optimal pieces for embedding and retrieval
Chunking Methods: 1. Fixed-size chunks (with overlap) - Size: 256-1024 tokens typically - Overlap: 10-20% to maintain context - Pro: Simple, predictable - Con: May cut mid-sentence 2. Semantic chunking - Split at natural boundaries (sentences, paragraphs) - Use NLP to find logical breaks - Pro: Better context preservation - Con: Variable chunk sizes 3. Recursive chunking - Try sentence splits first, then expand if needed - Respects hierarchical structure - Pro: Balances quality and simplicity - Con: More complex logic Example Chunk: { "id": "doc_123_chunk_5", "content": "RAG systems combine retrieval with generation...", "source": "documentation.pdf", "page": 15, "chunk_index": 5, "created_at": "2024-01-15T10:00:00Z", "version": 1 }

1.4 Embedding Generation

What it does: Converts text chunks into numerical vectors (embeddings)
Embedding Process: 1. Send chunk to embedding model API 2. Model generates dense vector (e.g., 1536 dimensions) 3. Store vector + metadata in vector DB 4. Index for fast similarity search Popular Embedding Models: ├── OpenAI text-embedding-3-large (3072 dim) ├── Claude text-embedding-3 (1024 dim) ├── Cohere embed-english-v3.0 (1024 dim) ├── open-source: all-MiniLM-L6-v2 (384 dim) └── Domain-specific: medical, legal, code embeddings Cost Consideration: - Small model (384 dim): Fast, cheap, lower quality - Large model (3072 dim): Slower, expensive, better quality - Batch processing for cost efficiency Typical Cost: ~$0.00002 per 1K tokens (for text-embedding-3-large) Processing 1M documents: ~$20-200 depending on size

What it does: Stores and indexes embeddings for fast similarity search

1.6 Indexing Strategy

What it does: Creates indices for efficient similarity search
Index Types: 1. HNSW (Hierarchical Navigable Small World) - Used by: Qdrant, Weaviate, Pinecone - Speed: ~O(log n) - Memory: High - Best for: General purpose 2. IVF (Inverted File) - Used by: Milvus, Faiss - Speed: Faster than HNSW with approximation - Memory: Lower - Best for: Large-scale 3. ScaNN (Learned Index) - Used by: Google, newer systems - Speed: Very fast - Memory: Optimized - Best for: Massive scale (billions) Trade-off: Speed vs. Accuracy - Exact search: 100% recall, slower - Approximate search: 95-99% recall, much faster - Production typically uses approximate

2. Retrieval Layer

Purpose

When a user query comes in, retrieve the most relevant documents/chunks from the vector database. This is the critical path that must be fast.

2.1 Query Embedding

What it does: Converts user query into embedding using same model as indexing
Process: 1. User submits: "How do RAG systems work?" 2. Send to embedding model 3. Get vector: [0.234, -0.567, ...] 4. Search this vector against DB CRITICAL: Use same embedding model as indexing! Different models = incomparable vectors = bad results

2.2 Similarity Search

What it does: Finds most similar vectors to query vector
Similarity Metrics: 1. Cosine similarity (most common) - Measures angle between vectors - Range: -1 to 1 (higher = more similar) - Fast to compute 2. Euclidean distance - Geometric distance between points - Good for some embedding models - Slightly slower 3. Dot product - Simple inner product - Fast when vectors normalized Query Example: search_vector = embed("How do RAG systems work?") results = vector_db.query( vector=search_vector, top_k=10, // Return top 10 results filter={"source": "documentation"}, // Optional filters threshold=0.75 // Minimum similarity score )

2.3 Metadata Filtering & Hybrid Search

What it does: Combines semantic (vector) and keyword search
Hybrid Search Strategy: 1. Vector search finds semantically similar content 2. Keyword search (BM25) finds exact matches 3. Results merged and re-ranked Example Query: - Vector search: Find chunks similar to "RAG" - Keyword search: Find chunks containing exact term "RAG" - Combine: Results that appear in both ranked higher Filters Applied: ├── Document type (PDF, website, code) ├── Date range (modified in last 30 days) ├── Source (internal docs only) ├── Language ├── Author/department ├── Sensitivity level └── Custom metadata Benefits: - More precise results - Reduces hallucinations - Enforces security/privacy policies

2.4 Re-ranking

What it does: Improves quality of retrieved results
Re-ranking Process: 1. Get top-100 from vector search (fast but maybe not perfect) 2. Use cross-encoder model to score all 100 3. Re-rank by score 4. Return top-10 to generation Why? - Vector search is approximate (75-90% accuracy) - Cross-encoder is slower but more accurate - 2-stage approach: speed + quality Popular Re-rankers: ├── BGE Reranker (open source) ├── Cohere reranker ├── MixedBread reranker └── Custom trained models

2.5 Caching Layer

What it does: Caches frequent queries to reduce latency and cost
Cache Layers: 1. Query cache (Redis) - Cache full query results - Key: hash(query + filters) - TTL: 1 hour to 7 days - Hit rate: 10-30% for typical apps 2. Embedding cache - Cache query embeddings - Avoid re-embedding same queries - Hit rate: 30-50% 3. Vector search cache - Cache vector DB results - Most expensive operation - Hit rate: 20-40% Example Cache: cache_key = hash(query + user_id + filters) cached_results = redis.get(cache_key) if cached_results: return cached_results else: results = retrieve(query) redis.setex(cache_key, 3600, results) return results Cost Impact: - Cache hit reduces cost by 90% - 20% hit rate = ~15% cost reduction - Also 10-100x faster

3. Generation Layer (LLM)

Purpose

Takes retrieved context + user query and generates an answer using a large language model.

3.1 Prompt Engineering

What it does: Constructs the prompt sent to LLM with context
Prompt Structure: ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━ System Prompt (defines behavior): "You are a helpful assistant answering questions based on provided documents. Be accurate and cite your sources. Do not make up information." Retrieved Context: "Document 1: RAG systems combine retrieval... Document 2: Embeddings are numerical... Document 3: Vector databases store..." User Query: "How do RAG systems work?" ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━ Full Message: System: [system prompt] Context: [retrieved docs] User: [query] Key Techniques: 1. Chain-of-thought: Ask LLM to reason step-by-step 2. Few-shot examples: Show example Q&A 3. Format specification: "Return as JSON/HTML" 4. Source attribution: "Cite which document" 5. Guardrails: "Only use provided context"

3.2 LLM Service / Inference Engine

What it does: Calls the language model to generate answer
LLM Options: 1. Cloud APIs (Simple, no infrastructure) ├── OpenAI API (GPT-4, GPT-3.5) ├── Anthropic API (Claude) ├── Google Gemini API └── Cohere Generate API Pros: Simple, latest models Cons: Cost per call, latency, vendor lock-in 2. Self-hosted (Full control, lower cost at scale) ├── Llama 2/3 on GPU cluster ├── Mistral on GPU cluster ├── Open-source models └── vLLM for serving Pros: Control, cost savings Cons: Infrastructure, maintenance 3. Hybrid (Balance) - Use local model for simple queries - Fall back to Claude/GPT for complex ones Typical Call: response = openai.ChatCompletion.create( model="gpt-4", messages=[ {"role": "system", "content": "You are..."}, {"role": "user", "content": "Context: ...\n\nQuestion: ..."} ], temperature=0.7, // 0-1: lower = deterministic max_tokens=500, top_p=0.9 )

3.3 Post-Processing

What it does: Refines LLM output before returning to user
Processing Steps: 1. Extract answer from response 2. Parse structured output (if JSON requested) 3. Validate answer quality 4. Extract citations 5. Clean up formatting 6. Add metadata Quality Checks: ├── Length check (too short/long?) ├── Relevance check (does it answer query?) ├── Confidence scoring (how confident?) ├── Hallucination detection └── Citation validation (does cite exist?) Example: { "answer": "RAG systems work by...", "confidence": 0.95, "citations": [ {"doc_id": "123", "chunk": 5, "text": "..."}, {"doc_id": "456", "chunk": 2, "text": "..."} ], "sources": ["documentation.pdf", "blog.md"], "generated_at": "2024-01-15T10:35:00Z" }

4.3 Message Queue (For Async Processing)

What it does: Handles asynchronous tasks
Used for: ├── Indexing documents (slow) ├── Re-embedding on updates ├── Batch processing ├── Webhooks and notifications └── Scheduled tasks Example Queue: User uploads document ↓ API adds job to queue: "index-document-123" ↓ Returns immediately (doesn't wait) ↓ Worker picks up job ↓ Chunks document ↓ Generates embeddings ↓ Stores in vector DB ↓ Updates status to "indexed" ↓ User notified via webhook Popular Queue Systems: ├── Kafka (high throughput, distributed) ├── RabbitMQ (classic, reliable) ├── AWS SQS (cloud, simple) ├── Bull (Node.js, in-memory) └── Celery (Python distributed tasks)

6. Quality & Evaluation

6.1 Hallucination Detection

What it does: Catches LLM making up information
Techniques: 1. Citation enforcement - Require answer to cite retrieved documents - Validate citations exist and are accurate - Reject answers without valid citations 2. Semantic similarity check - Compare generated answer to retrieved context - If too different, likely hallucinating - Threshold: > 0.7 similarity 3. Fact verification - Cross-reference facts against knowledge base - Use separate verification model - Ask: "Is this fact in the documents?" 4. User feedback loop - Collect thumbs down on answers - Flag as hallucination - Use for retraining/improvement Example: Question: "Who founded RAG?" Answer: "John Smith founded RAG in 2019" Retrieved docs: (no mention of John Smith) Result: HALLUCINATION DETECTED Action: Return error or "I don't know"

6.2 Relevance Scoring

What it does: Measures if results are actually relevant
Methods: 1. Ground truth dataset - Create Q&A pairs with expected results - Test retrieval against ground truth - Measure recall@k 2. User feedback - Collect thumbs up/down - Track which chunks marked as relevant - Improve retrieval based on feedback 3. BLEU/ROUGE scores - Compare generated answer to reference answer - Automated quality metric - Imperfect but useful Metrics: ├── Precision@10 (how many of top 10 are relevant?) ├── Recall@10 (of all relevant docs, how many in top 10?) ├── nDCG (normalized discounted cumulative gain) ├── MRR (mean reciprocal rank) └── F1 score (combined precision/recall) Typical targets: ├── Precision@10: > 0.8 (80% of results relevant) ├── Recall@10: > 0.7 (find 70% of all relevant) └── User satisfaction: > 4.0 / 5.0

6.3 Continuous Improvement

What it does: Identifies where system fails and improves
Feedback Loop: 1. User gets answer 2. Provides feedback (good/bad) 3. System logs the interaction 4. Analysts review bad cases 5. Identify root cause: - Bad embedding? - Bad chunking? - LLM error? - Missing document? 6. Fix identified issue 7. Test improvement 8. Deploy to production 9. Measure impact Common Improvements: ├── Re-train embedding model on feedback ├── Adjust chunking strategy ├── Improve prompt engineering ├── Add more documents to knowledge base ├── Implement better filtering ├── Upgrade to better LLM model └── Add more re-ranking layers

7. Security & Privacy

7.1 Access Control

What it does: Ensures users only see documents they should
Implementation: 1. Tag documents with access level 2. Store user permissions in database 3. On query, filter chunks by: - User's department - User's clearance level - Document owner - Public/private flag Example: User: "employee@company.com" (Engineering dept) Query: "salary information" System checks: Can this user access salary docs? - User is in Engineering dept - Salary docs are HR only - Result: ACCESS DENIED Filter at retrieval: retrieved_chunks = [ c for c in results if user_has_access(user_id, c.document_id) ]

7.2 Data Encryption

What it does: Protects sensitive data
Encryption layers: 1. Data at rest - Encrypt vector DB - Encrypt document store - Encrypt metadata - Use: AES-256 2. Data in transit - HTTPS/TLS for all API calls - Encrypt messages in queue - VPN for internal services 3. PII masking - Detect personally identifiable info - Remove/anonymize before embedding - Separate PII in secure storage

7.3 Audit Trail

What it does: Tracks who accessed what when
Logs for compliance: ├── User ID ├── Query executed ├── Documents accessed ├── Timestamp ├── IP address ├── Result └── Any data exported Used for: ├── Compliance audits ├── Security investigations ├── User behavior analysis └── Insider threat detection Retention: - Keep logs 1-7 years depending on regulation - Immutable storage (can't modify logs)

8.2 Cost Optimization

What it does: Reduces operational costs
Cost breakdown (typical): ├── Embedding API: 30% (most queries need embedding) ├── LLM API: 40% (longest inference) ├── Vector DB: 15% (storage + compute) ├── Compute: 10% (servers/containers) └── Other: 5% Optimization strategies: 1. Embedding caching - Cache embeddings of popular queries - Reduces embedding cost by 20-30% 2. Model selection - Use cheaper embedding model if quality OK - Use faster LLM for simple queries - Save large model for complex queries 3. Batching - Batch 50 documents for embedding - Reduce per-document overhead 4. Approximation - Use approximate search (95% recall) - vs exact search (100% recall) - 10x faster, same quality 5. Caching strategy - 1 day cache for non-urgent queries - 1 hour for real-time needs - Every 1% hit rate = ~1% cost savings Example costs (monthly): - 1M queries/month - 100 retrievals, 1 LLM call per query - Embedding: $30 (embedding model) - LLM: $50 (Claude 3 Sonnet) - Vector DB: $15 (Pinecone starter) - Compute: $100 Total: ~$195/month for 1M queries = $0.000195 per query

9. Real-World Challenges & Solutions

Challenge 1: Stale Knowledge
Problem: Documents become outdated Solutions: ├── Re-index frequently (daily) ├── Add document age to retrieval ├── Deprecate old versions ├── Use real-time data sources (APIs, streams) └── Let users flag outdated results
Challenge 2: Retrieval Failures
Problem: Relevant documents not retrieved Solutions: ├── Use multiple query strategies ├── Expand query with synonyms ├── Re-rank more aggressively ├── Increase top_k retrieved ├── Use hybrid (keyword + semantic) └── Retrain embedding model
Challenge 3: LLM Hallucinations
Problem: LLM makes up facts not in documents Solutions: ├── Require citations ├── Validate citations ├── Use constrained generation ├── Use smaller models (less hallucination) ├── Few-shot prompting └── Fact-checking step
Challenge 4: Latency
Problem: System is too slow (> 10s) Solutions: ├── Cache more aggressively ├── Reduce top_k retrieved ├── Use faster embedding model ├── Use faster LLM model ├── Approximate search ├── Pre-compute popular queries └── Optimize infrastructure
Challenge 5: Cost
Problem: Spending too much per query Solutions: ├── Use cheaper embedding model ├── Use cheaper LLM model ├── Cache results ├── Batch processing ├── Self-host where viable ├── Reduce embedding dimensions └── Monitor per-query costs

Summary: The Complete Picture

Offline: Indexing Pipeline

Extract Data → Clean → Chunk → Embed → Store in Vector DB ↓ Happens once, re-run on updates Batch processing, can be slow

Online: Query Processing (Critical Path)

User Query ↓ Embed Query (100ms) ← from cache if possible ↓ Search Vector DB (200ms) ← retrieve top-10 ↓ Re-rank Results (300ms) ← improve quality ↓ Generate Answer via LLM (3000ms) ← main latency ↓ Post-process & Format (50ms) ↓ Return to User Total: ~3.6 seconds

Key Takeaways

  • Embeddings are the currency — they must be consistent, high quality, and in the right dimensional space
  • Vector DB is the backbone — retrieval quality determines answer quality; garbage in = garbage out
  • Caching is critical — can reduce cost/latency by 10-100x; cache hits are gold
  • Quality is hard — hallucinations, stale data, bad retrieval require constant monitoring
  • Cost compounds — Every query has embedding cost + LLM cost; at scale, these add up quickly
  • Latency matters — Users expect < 10 seconds; optimize the LLM inference step first
  • Observability wins wars — Without logging/metrics, you're flying blind; good instrumentation pays for itself
  • Start simple, scale when needed — Use managed services first (Pinecone, Claude API); self-host only when you have the ops team
